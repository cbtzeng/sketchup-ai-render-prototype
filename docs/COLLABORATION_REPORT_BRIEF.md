# 協作報告（精簡版）
## 與 AI 共同開發 SketchUp 渲染外掛

> 本文為精簡版，收錄最關鍵的協作節點。
> 完整版（含全部案例、決策紀錄與評估細節）請見另附的 `collaboration.pdf`。

**專案**：SketchUp AI 渲染外掛 —— 在 SketchUp 行程內部擷取
beauty / hidden-line edge / fog depth 三張像素對齊的控制圖，
一起餵給 ControlNet，以求算圖時保住建築結構。

**GitHub**：https://github.com/cbtzeng/sketchup-ai-render-prototype

這份報告記錄的不是「AI 幫我寫了多少程式碼」，而是**判斷分歧的節點**與
**引導 AI 從錯誤中回復的過程**。多數分歧的共同主題是：
在時間有限時，如何判斷什麼該做、什麼不該做。

## 一、我推翻 AI 建議的三個節點

### 1. 拒絕接雲端 API，改走本機生成

**AI 的建議**：接 fal.ai 作為生成後端，理由是延遲低、適合互動式外掛。
整個雲端架構（job 狀態機、成本護欄、webhook 簽章驗證）都圍繞這個前提設計。

**當時的處境**：AI 明確告訴我它被五項未驗證的未知卡住 ——
端點路徑、多 ControlNet 參數結構、回應格式、webhook schema、計費單位。
那五項需要我去查文件，而我剩下的時間很短。

**我的判斷**：交付物是可用的外掛，而外掛需要的是「能生成圖」，
不是「能透過雲端生成圖」。花時間查外部 API 文件換來的只是架構完整度，
不會讓外掛多做到一件事。

**結果**：AI 重新評估後同意，並指出本機生成其實更適合這份作業 ——
完全可重現、可自由重跑。**五項未知一次消失。**
實作後在 M4 Pro 上跑通 SD1.5 + 雙 ControlNet，單張約 60 秒。

### 2. 質疑磁碟空間，抓到 AI 的估算錯誤

AI 說本機生成需要下載「約 7 GB」的模型，並開始背景下載。
我問了一句「你應該不會把我的硬碟塞爆對吧？我看容量剩下不多」。

**實際佔用是 25 GB。** 可用空間從 60 GiB 掉到 31 GiB。

原因是 AI 的下載腳本同時放行了 `*.safetensors` 與 `*.bin`（同一份權重的兩種格式），
又沒排除兩個程式根本用不到的完整 checkpoint：

| 檔案 | 大小 |
|---|---|
| `v1-5-pruned.safetensors` | 7.7 GB |
| `v1-5-pruned-emaonly.safetensors` | 4.3 GB |
| 各元件的 `.bin`（與 `.safetensors` 重複） | 4.0 GB |
| `safety_checker/`（程式碼傳 `None`，根本不載入） | 1.2 GB |

清除 21.56 GB 後回到 49 GiB。腳本改為**正面表列**要哪些檔案，
而不是負面表列排除什麼 —— 負面表列漏一項就多好幾 GB，而且不會有任何警告。

我想強調的是：**AI 的估算不會自我檢查**，
而「7 GB」與「25 GB」的差別在下載完成前沒有任何徵兆。

### 3. 把交付範圍收斂

我最初回答交付形式是「可安裝的 RBZ + demo 影片」加「repo + 文件 + 評估報告」。
AI 立刻標記這與我給的時間盒衝突，並指出兩者的力氣要花在完全不同的地方。

我改為只做後者。後續多次發揮作用 —— 例如決定跳過雲端部署時，
理由就是「這種交付物不需要真的部署」。

**這個節點的價值不在決定本身，而在 AI 主動把衝突指出來**，
而不是接受一個做不完的範圍然後兩邊都做半套。

## 二、我引導 AI 解決問題的過程

共同模式是：**我提供 AI 拿不到的資訊（實機執行結果、錯誤訊息、機器狀態），
AI 據此定位問題。** 幾乎每一個關鍵 bug 都是這樣被找出來的。

### 1. 「跑一半好像重開機了」→ 挖出記憶體管理的根因

我回報生成跑到一半機器重開。AI 最初懷疑是解析度太大。

我要求它再試，它改寫成**分階段的煙霧測試**（512 無控制 → 512 單控制 → 768 雙控制）。
前兩階段通過、第三階段 `MPS backend out of memory`。

錯誤訊息裡的「已配置 17.75 GiB」讓 AI 找到真正的原因：
**它的 pipeline 快取依控制組合各存一個完整模型**，
所以跑到第三個組合時記憶體裡躺著三份 SD1.5。正式跑批有四個條件，必爆。

但 UNet / VAE / text_encoder 在四個 pipeline 之間是同一份權重，
真正不同的只有 ControlNet。改成共用元件後降到 13.24 GiB。

**這個 bug 只有真的跑批才會現形** —— 單張測試永遠遇不到，因為只會建一個 pipeline。

接著 AI 跑了一個 (精度 × 解析度) 矩陣，全部組合都能跑。
但耗時揭露另一件事：768 只比 640 多 1.44 倍像素卻慢 **7 倍** ——
那不是計算量，是記憶體換頁。**勉強塞得下不等於跑得動。**
若只測「跑不跑得起來」而不量時間，就會選一個要跑 145 分鐘的設定。

### 2. 逐一回報 Ruby Console 的錯誤訊息

SketchUp 的 Ruby 環境有數個違反直覺的行為，全部靠我把錯誤訊息貼回去才被發現：

| 我回報的 | 查出的根因 |
|---|---|
| `LoadError: cannot load such file -- digest.so` | SketchUp 的 Ruby 幾乎沒有原生擴充檔 |
| `TypeError: reference to deleted DrawingElement` | `Face#pushpull` 會**刪掉原本那個面**，不是「把面推進去」 |
| `undefined method 'start_timer' for ArchitechRender::UI` | 自訂命名空間會遮蔽 SketchUp 的頂層 `::UI` |
| minitest 執行時 SketchUp 卡住 | `Minitest.run` 會掃 `$LOAD_PATH`；且 `$stdout` 的 `puts` 是 private method |

這些全都是 **AI 無法從文件推導出來的東西**。
它可以寫出看起來完全合理的程式碼，但只有在我的機器上執行才知道對不對。
我在這個專案裡的角色，很大一部分就是「那台能跑 SketchUp 的機器」。

## 三、AI 的錯誤有固定的形狀

記錄這些的理由是：認得出形狀就防得住。

**憑單次觀察下絕對結論。**
`require 'net/http'` 失敗一次，AI 就把可行性清單標成「實測：完全不可用」，
並斷言某個模組「已無存在意義」。我在同一台機器上跑另一支診斷腳本，全部載入成功。
AI 自己的檢討是：「這次的失誤不是臆造，是**過度概括單一次觀察**。」
處置方式改為**執行期實際驗證** —— 真的算一次已知雜湊並比對，而非檢查常數存不存在。

**用錯誤的方法驗證，得到錯誤的結論。**
AI 用 headless 瀏覽器截圖檢查 UI 面板，判定「420 px 下水平溢出」並改了 CSS。
實際上是該工具的視窗參數不影響排版寬度，它是用預設寬度排版後把截圖裁掉。
改用正確方法後版面完全正常，AI 撤回了基於誤判的修改。

**推理看起來完全合理，結果是錯的。**
面板只給使用者一個 fidelity 滑桿。AI 讓 `denoise` 隨它**反向**變動 ——
低保真給高 denoise（更自由）、高保真給低 denoise（更貼原圖）。
這個推理讀起來完全合理，我當下也覺得對。實測三組才發現兩端都不堪用：

| denoise | edge 權重 | 結構 | 外觀 |
|---|---|---|---|
| 0.65 | 0.74 | 完整 | 像截圖 |
| 0.79 | 0.48 | **量體整個跑掉** | 像照片 |
| **0.75** | **0.82** | **完整** | **材質光影被重畫** |

根本錯誤是把兩個**獨立的軸**綁在一起：`denoise` 決定模型能重畫多少外觀，
ControlNet 權重決定幾何要多貼合。**ControlNet 的整個意義就是讓這兩件事同時成立。**
同進同退等於把它的好處抵銷掉。

這個錯誤只有把三張圖擺在一起看才會發現。單看任何一張都會覺得「還行」。
**對生成式功能，「參數看起來合理」完全不能替代「把輸出攤開來比較」。**

## 四、我認為有效的協作模式

1. **要求 AI 標示信心等級。** 專案文件用 🟢/🟡/🔴 標記每一項 API 的確定程度。
   這讓「AI 不知道的事」變成可追蹤的清單，而不是散落在程式碼裡的隱性假設。
   最終從 10 項 🔴 降到 2 項。

2. **要求它寫下被否決的選項。** 決策紀錄的範本強制填寫「被否決的選項為什麼不行」。
   兩個月後回來看，需要的是這一段。

3. **不接受「應該可以」。** 每次 AI 說某個 API 或設定可行，
   我要求它給出實測數字或明確標記為未驗證。

4. **提供它拿不到的資訊。** 把錯誤訊息原文貼回去，比描述「好像壞了」有效得多。

## 五、成果與已知限制

**可實際使用。** 在 SketchUp 選單開啟面板 → 輸入 prompt →
擷取三個 pass（1024²，像素對齊）→ 本機 SD1.5 + 雙 ControlNet 生成 → 顯示結果。
單張約 60 秒，完全在本機執行，不需要網路或 API key。

實機驗證過的關鍵行為：三個 pass 像素對齊；
fog 深度圖為**精確線性的公制深度**（12 個標定點誤差 ≤ ±0.5 灰階）；
擷取後顯示設定完整還原，**例外發生時也還原**。

**已知限制**（完整版有詳述）：

| 限制 | 說明 |
|---|---|
| 記憶體競爭 | 使用者按 Render 時 SketchUp 本來就開著。這是把生成移到雲端的**主要理由** —— 不是為了速度，是為了不搶記憶體 |
| 生成品質天花板 | SD1.5 在 640² 是「算圖」而非「截圖」，但離 photoreal 有距離 |
| 雲端層未部署 | 狀態機、成本護欄、schema 已完成並通過 215 個測試，但沒寫 Supabase adapter |
| 評估樣本不足 | 只有 2 個程式產生的場景，缺曲面、玻璃、細長構件 |

我認為誠實標示邊界，比呈現一個看似完整的成果更有意義。
