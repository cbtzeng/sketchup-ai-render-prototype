# fog 範圍取自整個 model bounds，在大場景會浪費灰階動態範圍

## 觀察

`run_tests_staged.rb` 在一個只有預設人形元件的新模型上跑，
`Passes::Depth.fog_range` 回報 **6.56 m ~ 8.71 m**（來源 `bounds`）。

在這個空模型上是對的。但這個取法在真實場景會出問題。

## 問題

`fog_range` 的實作是取 `model.bounds` 的 8 個角點對相機的歐氏距離，
取 min/max 當作 fog 的起訖。這有兩個缺陷：

1. **用的是整個模型的包圍盒，不是畫面內看得到的東西。**
   建築模型常有基地範圍、參考底圖、遠處的環境量體。
   若基地跨 200 m 但鏡頭只拍一個 20 m 的中庭，
   fog 範圍會是 0–200 m，中庭只佔 **20/200 = 10%** 的灰階範圍 ——
   8-bit 量化後主體只剩約 **25 個灰階**，深度圖的解析度大幅損失。

2. **相機後方的幾何也會被計入。** `eye.distance(corner)` 是歐氏距離，
   不分前後。相機背後 50 m 有東西，`far` 就變成 50 m，即使它根本不在畫面裡。

## 這不是正確性問題，是品質問題

`fog_start_inches` / `fog_end_inches` 有寫進 metadata，
評估端隨時能把灰階換算回正確的公尺數。所以深度值不會**錯**，
只是**精度變差** —— 主體的深度階梯變粗，ControlNet 收到的深度訊號變弱。

## 候選解法

| 解法 | 成本 | 效果 |
|---|---|---|
| A. 維持現狀（model bounds） | 0 | 大場景時精度差 |
| B. 只算相機視線方向的投影距離，濾掉背後幾何 | 低 | 修掉缺陷 2，不修缺陷 1 |
| C. 用粗網格 raytest（如 32×32）取畫面內實際深度範圍 | 中 | 兩個缺陷都修，但需先量 raytest 速度 |
| D. 讓使用者在面板上手動設定遠近 | 低 | 把問題丟給使用者，但專業工具這樣做並不奇怪 |

## 目前決定

**MVP 維持 A，但列為已知限制**，並在 metadata 記錄 `fog_range_source`
讓評估報告能區分。理由：2 天時間盒下，這是品質優化而非阻斷性問題，
而且評估用的 12 個場景是我們自己建的，可以避開極端的尺度落差。

**若評估發現 depth 組表現不如預期，第一個要懷疑的就是這裡** ——
不要先去調 ControlNet 權重。

## 未解

- C 方案需要先量 `model.raytest` 的速度（可行性清單 3.9 原本標為「不再需要」，
  因為 fog 可用。現在它以另一個理由回來了：不是當深度圖，是當「決定 fog 範圍」的探針）。
- 32×32 = 1024 次 raytest 若能在 200 ms 內完成，C 方案就值得做。
