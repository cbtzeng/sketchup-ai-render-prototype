# 上傳完整性校驗從「PUT 回應」移到「建 job 時」

## 背景

`net/uploader.rb` 初版寫死一條規則：上傳後必須從 PUT 回應取得 sha256 並比對，
**沒回 sha256 就視為失敗**。當時的理由是「無法驗證」和「驗證通過」是兩回事，
不做樂觀假設。

理由本身沒錯，但實作的位置錯了。

## 問題

寫雲端端點時發現：**Supabase Storage 的簽名 URL 上傳幾乎確定不會回傳 checksum。**
（這一項仍標 🔴 未實測，但 S3 相容的簽名上傳普遍不回。）

如果不回，Ruby 端那條規則會讓**每一次上傳都被判失敗**，功能完全無法使用。
這是兩個在不同時間寫的模組互相矛盾 —— 各自看都合理，接起來就不通。

## 決定

**保證不變，位置改變。**

1. Ruby 端本機算出 sha256（不變）。
2. 上傳時若儲存體有回 checksum 就當場比對 —— 提早一步發現問題，沒理由放棄。
3. **沒回也不算失敗。**
4. sha256 隨 `create_job` 的 `controls` 欄位送上雲端（本來就有送）。
5. **雲端在建 job 時從儲存體重算並比對，不符回 `JOB-42` 且不計費。**

## 理由

核心保證是「壞掉的控制圖絕對不能一路送進 ControlNet」。這個保證在新設計下**完全成立** ——
只是檢查點從「上傳當下」移到「建 job 當下」，中間差幾百毫秒，而且 job 還沒送出去、
還沒計費。

而且新位置**更強**：雲端是從儲存體實際讀回來重算的，
驗的是「provider 等一下會讀到的那份資料」，比驗「我送出去的那份」更貼近真正要保護的東西。

## 被否決的選項為什麼不行

- **改 Ruby 端接受「校驗延後」但不做任何檢查**：等於放棄保證。
- **加一個 `POST /v1/uploads/:id/verify` 端點**：多一次往返、多一個端點、多一個失敗模式，
  而 `POST /v1/jobs` 本來就要讀那些物件，順手驗即可。
- **走自家上傳代理**：所有圖流經我們的 function，頻寬與冷啟動成本都上去了，
  而且簽名 URL 直傳的整個好處就沒了。

## 未解

`upload_batch` 的傳遞已一併修正（`request_upload_urls` 回傳 → `create_job` 帶回去）。
少了它，雲端只能猜「該使用者最近一個未認領的批次」——
同一帳號在兩台機器同時擷取會取錯批次，把別人的控制圖接到你的 job 上。

但 `001_init.sql` 目前**沒有 `upload_batches` 表**，需要補一個 migration。
