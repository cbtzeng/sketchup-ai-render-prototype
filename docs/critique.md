# critique.md — 反駁你的產品論點

你的論點：「多數 AI 渲染外掛只送一張 viewport 截圖，結構容易走鐘；外掛在 SketchUp 內部拿得到 3D 資訊，
所以做 beauty / hidden-line edge / fog depth 多重控制，換取更高結構保真度。」

我同意大方向，但以下七點我認為有問題。按嚴重程度排序。

---

## 1. 【最嚴重】edge 和 depth 這兩張圖，外部工具用一張截圖也生得出來——你選的兩個 pass 恰好是護城河最淺的

- **Edge**：對 beauty 截圖跑 Canny，就是一張 edge control。品質對建築這種硬邊場景其實不差。
- **Depth**：對 beauty 截圖跑 MiDaS/Depth-Anything，就是一張 depth control。而且——關鍵——
  **ControlNet 的 depth 模型本來就是用 MiDaS 這類相對深度訓練的**，所以估計出來的深度反而是 in-distribution，
  你的 fog 深度是 out-of-distribution。

也就是說，你挑的兩個 pass，一個是「外部做得到」，另一個是「外部做得到，而且可能更相容」。
競品「只送一張截圖」不代表他們拿不到 edge/depth，他們可能在雲端就跑了預處理器。

**你真正的護城河在你沒列進去的東西**：
- **材質 / 物件語意遮罩**：哪些像素是玻璃、哪些是木頭、哪個 group 是「沙發」。這是模型看圖猜不準、但 SketchUp 直接知道的。這才是外部完全複製不了的。
- **相機真值**：焦距、位置、朝向是精確數字，不是估計。可以算出真實消失點、做多視角一致性。
- **物理正確的公制深度**：hidden-line 邊線是真的遮擋邊界，不是梯度邊界。窗框後面那條被玻璃反光蓋掉的線，Canny 找不到，SketchUp 知道。
- **任意解析度 / 任意寬高比重繪**：不受 viewport 限制。

**建議**：不要放棄 edge/depth（它們是必要基礎），但把 **語意遮罩** 提到論點的第一位，
並在評估裡明確加入 B 組（外部 Canny/MiDaS）作對照。
如果 C 打不贏 B，你的論點就必須改寫成「護城河在語意，不在幾何」。
`spec.md` 的評估設計已經把 B 組列為必要，就是為了逼自己面對這件事。

## 2.（已實測更新）fog 給的是**精確公制深度**，這比我原本擔心的好；但分布問題依然存在

**原本的擔憂**：fog 可能非線性、單位不明、與 ControlNet 的期待分布不符。

**實測結果（2026-09-04，journal 003）**：前兩項不成立，第三項成立。

- fog 是**精確線性**的：`grey = 255 × (1 − (d−start)/(end−start))`，
  12 個標定點誤差全部 ≤ ±0.5 灰階（即 8-bit 量化誤差本身）。
- 單位是英吋，寫入值精確保留，可無損反推公尺數。
- 背景與遠距離連續，沒有深度斷層。

**這反而強化了論點**，而且強化的方式跟我在第 1 點說的一致：
MiDaS 那類單目估計給的是 scale/shift invariant 的**相對視差**；
我們給的是**公制絕對深度**。這確實是外部工具拿一張截圖做不到的事 ——
它不需要估計，它是從幾何直接讀出來的。

**但第三項擔憂依然成立**：ControlNet 的 depth adapter 多以 MiDaS 類的視差
（≈1/z、per-image 正規化）訓練。把線性公制 z 直接餵進去，
近景會被壓扁、遠景被拉伸，模型可能理解成「一堵牆」而不是「一條走廊」。

**處置**：轉換本身是小事（`disparity = 1/d` 再正規化），
但**哪一種正規化能讓模型表現最好是實驗問題，不是推導問題**。
已列為 Phase 4 的受測變因（C1：線性 z 正規化 / C2：轉視差後正規化），擇優並在報告中呈現差異。

**結論**：這一點從「可能致命的風險」降級為「一個需要調的參數」。

## 3. 「結構保真度」不是使用者真正買單的東西

建築師要的是「能拿去給業主看」。一張結構 100% 對、但材質質感平庸、光影生硬的圖，
輸給一張牆歪了 2 度、但氛圍動人的圖。

控制條件加得越多，生成模型的自由度越低，越容易產出「線稿上色」的死板結果。
你可能會贏了 Edge F-score，輸了成交。

**這就是為什麼 `spec.md` 把人類偏好列為守門指標 H2，而不是次要指標。**
只回報 Edge F1 提升的報告，在懂行的面試官眼中是不完整的——他會問「那圖好看嗎」。
先準備好答案。

## 4. 「多送幾張圖」本身有成本，你的定價論述還沒成立

- 擷取多 pass 要切換 rendering options、重繪、寫檔，可能加 2–5 秒，而且**畫面會閃**（使用者會覺得外掛在亂搞）。
- 多張控制圖 = 更多上傳頻寬 + 更多 conditioning 計算 = 更貴、更慢。
- 支援多 ControlNet 的端點通常比單純 img2img 端點少、貴、且較不穩定。

如果多重控制讓延遲從 20s 變 45s、成本從 $0.03 變 $0.08，
「結構準一點」值不值這個價，需要數字支撐，不能只靠直覺。
`spec.md` 因此把「成本增幅 ≤ 1.6×」與「p95 ≤ 90s」列為驗收條件——如果超了，論點在商業上就有問題。

## 5. 【已被證實低估】最大的競品是 SketchUp 自己，而且它不受 Ruby API 限制

我原本要說的是「把競品講弱，是面試中最容易被反問倒的地方」。掃描本機後，這件事已經成立：

**SketchUp 2026 內建了 `su_diffusion` —— Trimble 自家的 AI Render 功能**，
位於 `~/Library/Application Support/SketchUp 2026/SketchUp/Plugins/su_diffusion/`。

看它的組成，有兩個對你極為不利的事實：

1. **它是原生 C++/Qt 擴充，不是 Ruby 外掛。**
   目錄裡是 `SketchUpDiffusion.bundle` / `.so`（分 Qt 6.5.2 / 6.7.0 / 6.9.0 三版），
   Ruby 部分只有 5 個加密的 `.rbe`（`susdRoot` / `susdAna` / `susdRootProxy` / `update_scene` / `su_loader`）。
   **代表 Trimble 可以直接碰渲染引擎內部** —— 包括你拿不到的 depth buffer、G-buffer、材質 ID。
   你用 fog 模擬深度是因為 Ruby API 沒有 z-buffer；**它不需要這個 workaround**。

2. **它有 `.susig` 簽章、是 shipped extension，預設就在每個使用者的機器上。**
   你的外掛要說服使用者裝一個第三方外掛，來做一個「開箱即有」的功能。

**這對你的論點有兩個後果：**

- **好消息**：它證明「AI 渲染要跑在 SketchUp 內部」這個方向 Trimble 也同意，你的前提站得住。
- **壞消息**：「拿得到 3D 資訊」不再是你的差異化 —— 內建的那個拿得比你多。
  你的差異化必須改成 **Trimble 沒有做、或做不好的事**：可控性（多 ControlNet 權重可調）、
  可換底模、語意遮罩驅動的局部重繪、以及**可量測的保真度**。

**行動建議（取代原本的「去裝競品」）**：
1. 先跑一次內建的 su_diffusion，截圖存證，記錄它的 UI 給了哪些控制項、出圖品質、耗時。
2. 抓封包看它上傳什麼（`.rbe` 加密、邏輯在原生碼，靜態分析成本高，攔 HTTPS 比較快）。
3. **把 su_diffusion 當成評估的第四組 D**，和 A/B/C 一起跑同一批 36 shots。
   「我把自己的方案和 SketchUp 內建的 AI Render 做了配對比較，數據在這裡」——
   這一句話在面試裡的份量，超過任何功能 demo。

順帶：同目錄還有 `su_assistant`（Trimble 的 AI 助理）。Trimble 在這條線上的投入不小，
簡報時最好預期到「你和內建功能差在哪」這個問題。

## 6. 架構上的矛盾：BYO key 和雲端 key 保管不能同時成立

你寫「雲端做 job orchestration 與 **key 保管**」，又寫「**自備 key**」。這兩個是不同的信任模型：
- **BYO key**：使用者的 key 要從哪走？存在 Ruby 端不安全、存在你的雲端等於你在保管別人的 key（責任重大）、
  存在 HtmlDialog 的 localStorage 更糟。而且 BYO key 下你無法做成本護欄，因為燒的不是你的錢，但錯誤是你的鍋。
- **平台 key + 額度**：你保管自己的 key，對使用者發額度。成本護欄、快取、去重才有意義。

**建議**：原型走「平台 key + 固定測試額度」，架構文件裡把 BYO key 列為未來選項並說明其取捨。
面試時能講清楚兩者差異，比實作了半套更有分。

## 7. 三個 pass 的像素對齊，是整個方案的單點故障

若 `write_image` 在寬高比不符時的行為不可預期（可行性清單 1.4，我標為 🔴），
三張控制圖差幾個像素，ControlNet 會收到互相矛盾的條件，**結果可能比純 img2img 更差**。
也就是說，這個方案沒有「效果普通」的中間地帶，它要嘛明顯更好，要嘛明顯更糟。

**建議**：把「棋盤格角點誤差 ≤ 1 px」的對齊測試當成第一個寫的測試，而不是最後才驗。

## 我認為仍然成立的部分

上面全是反駁，但論點的核心我認為是對的，值得做：

- 「外掛在 SketchUp 內部 → 有外部拿不到的資訊」**方向正確**，只是你舉的例子（edge/depth）舉錯了強度，
  最強的例子是**語意遮罩與相機真值**。
- 「用可量測的方式證明它」**非常正確**，而且這正是多數面試作業缺的。
  一份帶配對 CI、帶對照組 B、還誠實回報 H2 可能不過的報告，比一個功能更多的 demo 有價值得多。
- 薄 Ruby 層 + 雲端編排的分層**正確**，理由是 SketchUp 單執行緒與更新不易。

**一句話總結我的反駁**：
你的論點不夠強的地方不是「錯」，是「你選了最容易被外部工具複製的那兩張控制圖來證明它」。
把語意遮罩加進來，並且老實跑 B 組對照，這份作業的說服力會高一個等級。
