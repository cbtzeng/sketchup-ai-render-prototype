## 摘要

本專案為 SketchUp 的 AI 渲染外掛原型，核心論點是：
**外掛跑在 SketchUp 行程內部，可以主動切換 rendering options 產生多張幾何對齊的
控制圖（beauty / hidden-line edge / fog depth），一起餵給 ControlNet 以提高結構保真度。**

開發全程與 AI（Claude）協作。這份報告記錄的不是「AI 幫我寫了多少程式碼」，
而是**判斷分歧的幾個關鍵節點**，以及**引導 AI 從錯誤中回復的過程**。
其中多數分歧的共同主題是：**在時間有限時，如何判斷什麼該做、什麼不該做。**

交付物是**一個可實際使用的 SketchUp 渲染外掛**。評估實驗是佐證工具，
用來檢查「多重控制圖是否真的提高結構保真度」這個設計假設 ——
它服務於外掛的設計決策，不是專案本身的目的。

## 1. 我推翻 AI 建議的四個節點

### 1.1 拒絕接 fal.ai，改走本機生成

**AI 的建議**：在規劃階段的 Q6，AI 建議接 fal.ai 作為生成 provider，
理由是延遲低、適合互動式外掛。整個雲端架構（job 狀態機、成本護欄、
webhook 簽章驗證、provider adapter 介面）都是圍繞這個前提設計的。

**我的判斷**：我問了一句「fal.ai 一定要的原因是什麼？」

當時的處境是：AI 明確告訴我它被五項未驗證的未知卡住（端點路徑、多 ControlNet
參數結構、回應格式、webhook schema、計費單位），而那五項**需要我去查文件**。
我剩下的時間很短。

**【請確認】** 我的判斷是：交付物是評估報告，而評估報告需要的是「能生成圖」，
不是「能透過雲端生成圖」。花時間查一個外部 API 的文件，換來的只是架構完整度，
不會讓報告多一個數字。

**結果**：AI 重新評估後同意，並指出本機生成其實**更適合這份作業** ——
完全可重現（託管 API 換模型版本不會通知你）、可自由重跑（找參數不用算錢）。
五項未知一次消失。

實作後在我的 M4 Pro 上跑通 SD1.5 + 雙 ControlNet，單張約 30 秒。

### 1.2 把交付範圍從 (a)+(b) 收斂到 (b)

**AI 的提醒**：我最初回答交付形式是「(a) 可安裝的 RBZ + demo 影片」加
「(b) repo + 文件 + 評估報告」。AI 立刻標記這與我給的 ≤2 天時間盒衝突，
並說「若是 (b)，評估報告比功能重要；若是 (a)，穩定性比評估重要」——
兩者的力氣要花在完全不同的地方。

**我的判斷**：改為只要 (b)。

**結果**：範圍衝突消失，AI 的優先序也跟著調整。這個決定在後續多次發揮作用 ——
例如決定跳過 Vercel 部署時，理由就是「(b) 型交付物不需要真的部署」。

### 1.3 質疑磁碟空間，抓到 AI 的錯誤

**背景**：AI 說本機生成需要下載「約 7 GB」的模型，並開始背景下載。

**我的判斷**：我問「你應該不會下載模型結果把我的硬碟塞爆對吧？我看容量剩下不多」。

**結果**：實際佔用是 **25 GB，不是 7 GB**。可用空間從 60 GiB 掉到 31 GiB。

AI 查出原因是它自己的下載腳本寫錯 —— `allow_patterns` 同時放行
`*.safetensors` 與 `*.bin`（同一份權重的兩種格式），又沒排除兩個
`from_pretrained` 根本用不到的單檔 checkpoint：

| 檔案 | 大小 | 為什麼不需要 |
|---|---|---|
| `v1-5-pruned.safetensors` | 7.7 GB | 單檔格式的完整 checkpoint |
| `v1-5-pruned-emaonly.safetensors` | 4.3 GB | 同上 |
| 各元件的 `.bin` | 4.0 GB | 與 `.safetensors` 重複 |
| `safety_checker/` | 1.2 GB | 程式碼傳 `safety_checker=None`，根本不載入 |

清除 21.56 GB 後回到 49 GiB。腳本改為**正面表列**要哪些檔案，
而不是負面表列排除什麼 —— 負面表列漏一項就多好幾 GB，而且不會有任何警告。

**【請確認】** 這一題我想強調的是：AI 的估算不會自我檢查，
而「7 GB」與「25 GB」的差別在下載完成前沒有任何徵兆。
（如果你當時的想法不同，請改寫。）

### 1.4 選擇捨棄 Vercel 部署

**AI 的分析**：AI 寫完部署步驟後，在文件開頭直接寫「現在部署上去會是空殼」——
雲端層的 `JobStore` 只有記憶體實作，而 **Vercel Function 是無狀態的**，
記憶體在兩次呼叫之間就消失。這不是「不完整」，是結構上不可能運作。

**我的決定**：捨棄。

**結果**：省下 1–2 小時（三個 Supabase adapter 的實作與除錯），
換去做真正的交付物。

## 2. 我引導 AI 解決問題的過程

這一節的共同模式是：**我提供 AI 拿不到的資訊（實機執行結果、錯誤訊息、
機器狀態），AI 據此定位問題。** 幾乎每一個關鍵 bug 都是這樣被找出來的。

### 2.1 「跑一半好像重開機了」→ 挖出 OOM 根因

我回報生成跑到一半機器重開。AI 最初懷疑是解析度（768×768）太大。

我要求它再試一次，它改寫成**分階段的煙霧測試**（512 無控制 → 512 單控制
→ 768 雙控制），結果是前兩階段通過、第三階段 `MPS backend out of memory`。

錯誤訊息裡的「已配置 17.75 GiB」讓 AI 找到真正的原因：**它的 pipeline 快取
依控制組合各存一個完整模型**，所以跑到第三個組合時記憶體裡躺著三份 SD1.5。
而正式跑批有 A/B/C1/C2 四個條件，必爆。

但 UNet / VAE / text_encoder 在四個 pipeline 之間是同一份權重，
真正不同的只有 ControlNet。改成共用元件後降到 13.24 GiB。

**這個 bug 只有真的跑批才會現形** —— 單張測試永遠遇不到，因為只會建一個 pipeline。

### 2.2 「768 能跑」不等於「768 該用」

共用元件後 AI 跑了一個 (dtype × 解析度) 矩陣，全部組合都能跑。
但耗時揭露了另一件事：

| 設定 | 耗時 | 48 張推估 |
|---|---|---|
| float16 768 | **180.8 s** | 145 分鐘 |
| float32 640 | 31.8 s | 25 分鐘 |

768 只比 640 多 1.44 倍像素卻慢 **7 倍** —— 那不是計算量，是記憶體換頁。
**勉強塞得下不等於跑得動。** 若只測「跑不跑得起來」而不量時間，
就會選一個要跑 145 分鐘的設定。

### 2.3 逐一回報 Ruby Console 的錯誤訊息

SketchUp 的 Ruby 環境有數個違反直覺的行為，全部是靠我把錯誤訊息貼回去才被發現：

| 我回報的 | 查出的根因 |
|---|---|
| `already initialized constant EDGE_COLOR_MODE` | AI 用字串替換插入新常數時，沒發現同名常數已存在 |
| `LoadError: cannot load such file -- digest.so` | SketchUp 的 Ruby 幾乎沒有原生擴充檔 |
| `LoadError: cannot load such file -- socket.so` | 同上，`net/http` 因此不可用 |
| `TypeError: reference to deleted DrawingElement` | `Face#pushpull` 會**刪掉原本那個面**，不是「把面推進去」 |
| minitest 執行時 SketchUp 卡住 | `Minitest.run` 會掃 `$LOAD_PATH`；且 `$stdout` 是 `Sketchup::Console`，其 `puts` 為 private |

**【請確認】** 我想強調的是：這些全都是 AI 無法從文件推導出來的東西。
它可以寫出看起來完全合理的程式碼，但只有在我的機器上執行才知道對不對。
（如果你有更想強調的角度，請改寫。）

### 2.4 手動測試推翻 AI 的設計假設

AI 問我 rendering_options 的改動會不會污染 undo stack，我先憑印象回答「會」。
AI 要求實測（畫一個矩形 → 改設定 → 按 Ctrl+Z → 觀察撤銷了什麼）。

實測結果：**撤銷掉的是矩形，顯示設定維持改過的狀態。** 我的推測是錯的。

這個結果反而更嚴重：因為 rendering_options 不在 model transaction 內，
**SketchUp 不會幫我們還原任何東西**。程式當掉或有人拿掉 `ensure` 區塊，
使用者的樣式設定就永久壞掉，而且他自己按 Ctrl+Z 也救不回來。

因此 `ViewState` 只暴露 `with_temporary`，不開放裸的 `restore` ——
不給呼叫端「忘記還原」的機會。

## 3. AI 下錯結論、被實測推翻的幾次

記錄這些的理由是：**AI 的錯誤有固定的形狀**，認得出來就防得住。

### 3.1 憑單次觀察下絕對結論

`require 'net/http'` 失敗一次，AI 就把可行性清單標成「**實測：完全不可用**」，
並斷言「`Sketchup::Http` 是唯一選項，`NetHttpBackend` 已無存在意義」。

我在同一台機器上跑另一支診斷腳本，`digest` / `socket` / `net/http` **全部載入成功**。

AI 承認結論下得太早，改標為 🟡「不穩定，不可依賴」，並寫了一篇決策紀錄
（journal 008）記錄兩次相反的觀察。它自己的檢討是：
「這次的失誤不是臆造，是**過度概括單一次觀察**——同樣要避免。」

處置方式改為**執行期實際驗證**：`digest_util.rb` 不檢查常數存不存在，
而是**真的算一次 `sha256("abc")` 並比對已知值**來挑後端。

### 3.2 用錯誤的方法驗證，得到錯誤的結論

AI 用 headless Chrome 截圖檢查 UI 面板，判定「420 px 下水平溢出」並改了 CSS。

實際上是 headless Chrome 的 `--window-size` **不設定 layout viewport**，
它是用預設寬度排版後把截圖裁掉。改用 iframe 建出真正的 420 px viewport 後，
版面完全正常。AI 撤回了基於誤判加上的 CSS。

### 3.3 臆造 API 行為（而非名稱）

專案有一條硬規則是「不臆造 SketchUp API」。AI 沒有臆造**名稱**，
但臆造了**行為** —— 假設 `Face#pushpull` 之後原本的 Face 還有效。

它不是。`pushpull` 建立新幾何並取代原面，之後對原物件設材質就拋
`TypeError: reference to deleted DrawingElement`。

**【請確認】** 這一點我覺得值得寫進報告，因為「不臆造 API」這條規則
原本只防名稱，這次證明**行為也要防**。

### 3.4 其他

- 把 rendering_options 的 key 數量數成 58（實際 70）
- `next_attempt_at` 的語意方向寫反了 —— 只在「重送之後」寫入，
  導致第一次重試零退避，會對著剛掛掉的 provider 連打三次
  （這個是 AI 派出的另一個 subagent 在整合時發現的）

## 4. 我認為有效的協作模式

**【請確認】** 以下是我的觀察，請依你的實際感受改寫。

1. **要求 AI 標示信心等級。** 專案文件用 🟢/🟡/🔴 標記每一項 API 的確定程度，
   🔴 表示「需要在實機驗證」。這讓「AI 不知道的事」變成一個可追蹤的清單，
   而不是散落在程式碼裡的隱性假設。最終從 10 項 🔴 降到 2 項。

2. **要求它寫下被否決的選項。** 決策紀錄的範本強制填寫「被否決的選項為什麼不行」。
   兩個月後回來看，需要的是這一段。

3. **不接受「應該可以」。** 每次 AI 說某個 API 或設定可行，我要求它給出
   實測數字或明確標記為未驗證。這個習慣抓到了 fog 的線性度、
   `write_image` 的取景行為、二進位上傳的完整性等多項。

4. **提供它拿不到的資訊。** AI 沒有 SketchUp、沒有我的機器狀態。
   把錯誤訊息原文貼回去，比描述「好像壞了」有效得多。

## 5. 用實驗檢查自己的設計假設

外掛的核心設計賭注是「多重控制圖比單張截圖更能保住結構」。
這個假設如果不成立，外掛就該少做兩個 pass、跑得更快。所以我讓 AI 設計了一組
小規模的對照實驗來檢查它 —— **目的是驗證設計決策，不是產出研究成果**。

關鍵是對照組 B：**對 beauty 截圖跑 Canny 得到 edge control**。
這一組是 AI 在規劃階段堅持要加的，理由是：
> Canny 在外部工具用一張截圖就做得到。少了 B 組，就無法證明「必須跑在 SketchUp 內部」。

我當時同意了，並在 open-questions 的 Q8 預先決定：若 C 打不贏 B，
**誠實寫進報告並改寫論點**，而不是調整實驗設定直到有優勢。

第一批真實數據（n=2 shots，單一 seed）：

| 條件 | Edge F1 |
|---|---|
| A 純 img2img | 0.534 |
| **B 外部 Canny** | **0.778** |
| C1 多重控制（線性 z） | 0.724 |
| C2 多重控制（視差） | 0.721 |

**B 勝過 C。**

### 必須同時說明的限制

這個數字不足以下定論：

- n=2、單一 seed，信賴區間無意義
- 測試場景是程式產生的簡單量體：**無貼圖、直角、規則開口、邊緣乾淨**——
  這是**對 Canny 最有利的情境**。Canny 的弱點在貼圖雜訊與植栽，而這個場景兩者都沒有
- 真正的檢驗需要涵蓋曲面、大面積玻璃、細長構件的場景

### 但結論仍然成立

即使限制很多，這個結果證明了一件事：**「跑在 SketchUp 內部」這個優勢，
不會自動轉換成更好的結構保真度。** 它需要被證明，而目前還沒被證明。

如果沒有 B 組，我會看到「C（0.724）遠勝 A（0.534）」然後宣稱論點成立 ——
那是錯的結論，而且不會有任何人發現。

### 這對外掛的實際影響

短期不改變外掛的功能 —— 三個 pass 都留著，因為樣本數不足以支撐移除決定。

但它改變了**接下來該往哪裡投資**：如果 hidden-line 相對外部 Canny 沒有明顯優勢，
那麼真正值得做的下一個 pass 是**材質／物件語意遮罩**（哪些像素是玻璃、
哪個 group 是沙發）—— 那是外部工具拿一張截圖真的做不到的東西。
這一點在規劃階段的 `critique.md` 第 1 點就被 AI 指出過，
現在有了數據支持。

實驗的價值在於它**便宜地否定了一條路**，讓我不用在錯的方向上繼續投資功能。

## 6. 目前狀態與已知缺口

**已完成並經實機驗證**
- 三 pass 擷取管線（beauty / hidden-line / fog depth），像素對齊
- fog 深度圖確認為**精確線性的公制深度**（12 個標定點誤差 ≤ ±0.5 灰階）
- 本機生成（SD1.5 + 雙 ControlNet，MPS）
- 評估管線：擷取 → 生成 → 指標 → 配對統計 → 報告
- 雲端層：job 狀態機、成本護欄、Supabase schema（215 個測試通過，未部署）

**已知缺口**
- 外掛面板目前指向未部署的雲端，按 Render 走模擬後端，**不會產出真實算圖結果**
- 評估只有 2 個程式產生的場景，缺曲面／玻璃／細長構件
- 人類偏好 A/B 測試（spec 的 H2 守門指標）未做 ——
  **沒有它，「結構變準」的結論不完整**
